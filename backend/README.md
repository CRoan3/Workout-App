# Backend

Spring Boot 4 REST API (Java 17) backed by PostgreSQL. For how to install and run it, see the [root README](../README.md).

## Package structure

The code is organized **by layer**. All packages live under `src/main/java/com/chrisroan/workout/`:

| Package       | Contains                                   | Example                       |
|---------------|--------------------------------------------|-------------------------------|
| `controller`  | REST endpoints: URLs and HTTP in/out       | `ExerciseController`          |
| `service`     | Business logic and entity ↔ DTO mapping    | `ExerciseService`             |
| `repository`  | Database access (Spring Data JPA)          | `ExerciseRepository`          |
| `domain`      | JPA entities, one per table                | `Exercise`                    |
| `dto`         | Request/response shapes used by the API    | `ExerciseResponseDTO`         |
| `exception`   | Custom exceptions and the global handler   | `GlobalExceptionHandler`      |

Other locations:

```
src/main/resources/
├── application.properties     Configuration
└── db/migration/              Flyway migrations (V1__..., V2__..., ...)
src/test/java/...              Tests
```

## How a request flows

```
HTTP request
   │  JSON body → request DTO
   ▼
Controller      maps URL + method to a service call
   ▼
Service         business logic; loads/saves entities; maps entity → response DTO
   ▼
Repository      generated by Spring Data JPA from an interface
   ▼
PostgreSQL
```

The response DTO travels back up and is serialized to JSON. Any exception thrown along the way is turned into an HTTP error response by `GlobalExceptionHandler`.

## Layer conventions

### Controllers
- Keep them thin: read the path variables and body, call one service method, return the result.
- **Never return entities.** Return DTOs only, so the API shape stays independent of the database and lazy-loaded relationships don't leak.
- Annotate each controller with `@CrossOrigin(origins = "http://localhost:5173/")` so the frontend dev server can call it. **New controllers need this too**, or the browser blocks their requests.

### Services
- Own the business logic and the mapping from entity to response DTO (a private `mapToDTO` method).
- Throw domain exceptions (`ResourceNotFoundException`), not HTTP types. Services shouldn't import `HttpStatus` or `ResponseStatusException`; turning exceptions into HTTP responses is the web layer's job.

### Repositories
- Interfaces extending `JpaRepository<Entity, Long>`. Spring generates the implementation at runtime.
- Add query methods by naming convention (e.g. `findByWorkoutPlanId(Long id)`) before writing custom queries.

### Entities (`domain`)
- Mirror the database tables exactly. `spring.jpa.hibernate.ddl-auto=validate` makes startup fail if an entity and its table don't match.
- No setter for `id`; the database generates it.
- Relationships use `FetchType.LAZY`.
- `created_at` / `updated_at` are set by PostgreSQL (column defaults and the `set_updated_at()` trigger), so they're mapped with `insertable = false`.

### DTOs
- `...CreateRequestDTO` for incoming bodies, `...ResponseDTO` for outgoing data.
- When a DTO changes, update the matching TypeScript type in the frontend's `features/<feature>/api.ts`.

### Dependency injection
- Use **constructor injection** with `private final` fields, not `@Autowired` on fields. This makes dependencies explicit and the class easy to test.

## Error handling

`GlobalExceptionHandler` (`@RestControllerAdvice`) turns exceptions into [RFC 9457 Problem Details](https://www.rfc-editor.org/rfc/rfc9457) responses for every controller:

| Thrown                                  | Response                                                    |
|-----------------------------------------|-------------------------------------------------------------|
| `ResourceNotFoundException`             | **404**, with the message as `detail`                       |
| Spring MVC errors (bad JSON, wrong param type, wrong method) | **400 / 405**, via the `ResponseEntityExceptionHandler` base class |
| Anything else                           | **500** with a generic message; full stack trace is logged  |

To report a missing resource from a service:

```java
Exercise exercise = exerciseRepository.findById(id)
        .orElseThrow(() -> new ResourceNotFoundException("Exercise", id));
```

To add a new kind of error (e.g. a 409 Conflict): create an exception class in `exception/`, then add an `@ExceptionHandler` method for it in `GlobalExceptionHandler` that returns a `ProblemDetail`.

## Database and migrations

The schema is managed by **Flyway**. Migrations in `src/main/resources/db/migration/` run automatically on startup, before Hibernate validates the entities.

- To change the schema, add a new file with the next version: `V4__describe_the_change.sql` (capital `V`, two underscores).
- **Never edit a migration that has already been applied.** Flyway checksums each file and refuses to start if one changes.
- Don't change the schema by hand in pgAdmin. Every change goes through a migration so a fresh database can be rebuilt exactly.
- Changing an entity's columns always needs a matching migration, or `validate` fails at startup.

## Configuration

Settings live in `src/main/resources/application.properties`:

| Property                          | Value                       | Purpose                                  |
|-----------------------------------|-----------------------------|------------------------------------------|
| `spring.datasource.*`             | `localhost:5432/Workout_Tracker`, `postgres`/`postgres` | Database connection |
| `spring.jpa.hibernate.ddl-auto`   | `validate`                  | Check entities against the schema; never modify it |
| `spring.jpa.show-sql`             | `true`                      | Log generated SQL (useful in development) |

## Tests

```bash
./mvnw test        # Windows: .\mvnw.cmd test
```

Currently there's a single `contextLoads` test, which starts the whole application. **It needs PostgreSQL running**, because startup connects to the database and runs Flyway.

## Adding a new endpoint (checklist)

1. **Schema:** if new tables or columns are needed, add a Flyway migration.
2. **Entity:** add or update the class in `domain/` to match.
3. **Repository:** add an interface in `repository/` if it's a new entity.
4. **DTOs:** add request/response classes in `dto/`.
5. **Service:** add the logic and `mapToDTO`; throw `ResourceNotFoundException` for missing records.
6. **Controller:** add the endpoint, with `@CrossOrigin` if it's a new controller.
7. **Docs:** add the endpoint to the API table in the root README.
8. **Frontend:** mirror the DTOs and add the call in `features/<feature>/api.ts`.
9. Restart the backend and test the endpoint, including the error cases.

## Known gaps

- **No input validation yet.** Invalid bodies (e.g. a blank name) reach the database and fail as a 500. Planned: `@Valid` + Bean Validation annotations, returning 400s.
- **Duplicate exercise names return 500.** This should be a 409 Conflict.
- **`updatedAt` in the response to an update is stale.** The new value is set by a database trigger after the save, and the entity isn't refreshed.
- **CORS is configured per controller.** A single global CORS configuration would avoid repeating the origin.
